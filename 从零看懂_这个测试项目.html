二、一个请求的完整旅程

以"POST /transactions 记一笔账"为例，看看从你发出去到数据进库，中间到底发生了什么。这就是测试用例能想出来的根本依据。

你发出请求。测试脚本（或 Postman、或那个小前端）往 127.0.0.1:8000 发了一个 POST，body 里是 {"amount":100,"category":"food"}。 你的 test_02_transactions.py
uvicorn 收到。uvicorn 是"门童"，负责把网络上的字节流翻译成 HTTP 请求（方法、路径、头、body）。 uvicorn 进程
交给 FastAPI 应用。就是 app/main.py 里那个 app = FastAPI() 对象。 app/main.py
查路由表。FastAPI 看"POST + /transactions"这个组合，找到注册过的处理函数 add_transaction。 app/routes/transactions.py
先执行"依赖"。函数的参数里有 user_id: int = Depends(get_current_user)，FastAPI 会先跑它：读 Authorization 头 → 验证 JWT 签名 → 取出里面的 sub（用户 id）。
同时跑 get_db 开一个数据库连接。
token 不对就在这一步直接 401，函数体根本不会执行——这就是为什么"没带 token"不会报 422。 app/auth/auth.py、app/database/database.py
再校验 body。把你传的 JSON 交给 Pydantic 模型 Transaction：amount 必须 > 0，category 长度 1~100。
不合规就 422，函数体同样不执行——所以 422 是"框架在门口就把你拦下了"。 app/schemas.py
真正执行业务。进入 add_transaction 函数体：组装一个 TransactionDB 对象，把 user_id 从 token 里拿到的值塞进去（注意：不接受你传的 user_id）。 app/routes/transactions.py
SQLAlchemy 翻译成 SQL。db.add() + db.commit() → 翻译成 INSERT INTO transactions (...) VALUES (...)。 app/database/models.py
SQLite 写入。数据真的落进 finance.db 这个文件，并返回新记录的 id。
序列化返回。函数返回对象 → FastAPI 按 response_model=TransactionOut 转成 JSON → 加状态码 201 返回给你。
这 10 步，就是你所有用例的来源：
旅程中的哪一步对应的用例
第 5 步（鉴权）没 token → 401；token 过期 → 401；伪造 → 401
第 6 步（校验）金额 0/负数/null/字符串 → 422；分类空/超长 → 422
第 7 步（业务）属主被强绑 → 塞别人 user_id 也没用（TRX-019）
第 9 步（落库）写入成功 → 再查能查到；统计同步变化
第 10 步（序列化）响应字段完整性、类型是否正确

三、一次测试的完整旅程

你在终端敲了 python -m pytest api_test，然后屏幕上就滚出一堆 PASSED。这中间发生了什么？

pytest 启动，读配置。找到 api_test/pytest.ini：testpaths = tests（只扫 tests 目录）、pythonpath = .（让 from utils.assertions import ... 能找到）。 pytest.ini
收集用例。扫 test_*.py 文件 → 打开 → 找名字以 test_ 开头的函数 → 每个函数算一个"用例项"。
所以命名规则不是随便定的：不加 test_ 前缀，pytest 就当没看见。
加载 conftest.py。pytest 会自动把测试目录上层所有 conftest.py 加载进来，里面的 @pytest.fixture 就变成了"可用零件"。 api_test/conftest.py
先跑 session 级的自动 fixture。我们的 check_server_up 是 autouse=True + scope="session"：整个测试开始前只跑一次，先访问 / 探活。服务没起就直接停下，给出人话提示。
逐条执行用例，按参数名找 fixture。比如 def test_x(client, base_url, user)：
· client → 找 session 级 fixture，只建一次
· base_url → 同上
· user → 找 function 级 fixture，每条用例都新建一个（所以每条用例都是独立新账号）
执行 user 这个 fixture。调 _register_and_login()：生成随机邮箱 → POST /register → POST /login → 拼出 headers → 交给你。
你在函数里只写了 user 四个字母，背后跑了两个真实请求。
执行函数体。r = client.post(...) 发真实请求，assert_status(r, 201) 判断。
判定。所有 assert 都成立 → PASSED；任何一个不成立 → FAILED，并打印实际值 vs 期望值。
一个函数报错不影响其它用例继续跑——这是 pytest 和"一个脚本跑到底"最大的区别。
汇总。最后一行 63 passed in 15.8s。数字就是你的成果，也是简历上的量化数据。
为什么每条用例一个新账号？
因为 POST /register 对已存在的邮箱返回 400。如果所有用例共用一个账号，第 2 条用例就会因为"邮箱已注册"而失败——失败原因还跟被测功能无关，这叫"用例互相污染"。
用 uuid 随机邮箱 + function 级 fixture，就彻底解决了。

六、三个核心技巧：为什么这么写

技巧 1：fixture —— 别每次手动造账号

❌ 不用 fixture

每条用例都写一遍：
  随机邮箱
  POST /register
  POST /login
  拿 token
  拼 headers
  ...然后才开始测

20 条用例 = 重复 20 遍，改一处要改 20 处

✅ 用 fixture

def test_x(client, base_url, user):
    r = client.get(..., headers=user["headers"])

背后自动跑注册+登录，你只写四个字母

本质：把"准备工作"从用例里抽出去，一处维护，处处复用。这就是测试框架和"一堆脚本"的区别。

技巧 2：表驱动 —— 别复制粘贴用例

# 一张表 = 8 条用例
@pytest.mark.parametrize("payload, field", [
    ({"email": "v1@x.com", "password": "1234567"}, "password"),   # 密码 7 位
    ({"email": "not-an-email", "password": "Passw0rd!23"}, "email"),
    # ... 再写 6 行
], ids=["AUTH-003", "AUTH-007", ...])
def test_register(client, base_url, payload, field):
    r = client.post(f"{base_url}/register", json=payload)
    assert_validation(r, field)

为什么好：① 数据集中，一眼看出测了哪些情况 ② 加一条用例只是加一行 ③ 不会被复制粘贴时漏改某个值。

技巧 3：断言封装 —— 失败时告诉你发生了什么

❌ 裸断言

assert r.status_code == 422

AssertionError: assert 500 == 422
然后你就懵了：为什么是 500？

✅ 封装后

assert_validation(r, "amount")

请求: POST /transactions
请求体: {"amount": "abc"}
期望: 422  实际: 500
响应体: {"detail": "Internal Server Error"}

记住这个投入产出比：写封装要 10 分钟，省下的排障时间是几十个小时。

七、最容易混的 8 组概念

对比区别怎么记
400 vs 422 400 = 业务上办不了（邮箱重复）；422 = 格式不对（密码太短） 422 是框架在门口拦的，400 是代码里手动抛的
401 vs 403 401 = 你没证明你是谁；403 = 知道你是谁，但不许你干 这个项目不用 403，跨用户访问返回 404（故意不告诉你东西存不存在）
PUT vs PATCH PUT = 整体替换（少一个字段就 422）；PATCH = 只改传了的字段 这项目只有 PUT，所以"只改金额"必须把分类一起传
路径参数 vs query 参数 vs body /transactions/7（路径）｜?month=2026-05（query）｜{"amount":100}（body） 指明"哪一个"用路径；"筛选"用 query；"提交内容"用 body
镜像 vs 容器 镜像 = 安装光盘（只读模板）；容器 = 用光盘装出来正在跑的程序 docker pull 下载镜像；docker run 启动容器
假成功 vs 报错 假成功 = 返回 200 但事情没做（如改了 date 没存库）；报错 = 明确告诉你失败 假成功更危险，因为没人会发现
冒烟 vs 回归 冒烟 = 核心链路能不能跑（P0，几分钟）；回归 = 全部用例再跑一遍（防止改坏旧功能） 上线前跑冒烟；每次改代码跑回归
测试用例 vs 测试脚本 用例 = 一句话描述"做什么、期望什么"；脚本 = 那句用例的可执行版本 一条用例可以写成脚本，也可以手工执行
